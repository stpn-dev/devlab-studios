# Admin password change — design

Date: 2026-09-17
Status: Approved for planning

## Problem

Admin credentials live only in Cloudflare secrets (`ADMIN_EMAIL` +
`ADMIN_PASSWORD_HASH`, or `ADMIN_USERS`). Changing a password means running
`npm run cms:hash-admin-password` in an interactive terminal, then updating a
secret in the dashboard or via `wrangler secret put`.

That cost is not hypothetical. On 2026-09-17 the production hash was still in
a retired `sha256` format, which `verifyPassword` refuses, and the owner was
locked out of `/admin` until the hash was regenerated by hand. A password that
can only be rotated by an operator with a terminal is a password that does not
get rotated.

## Constraint that shapes the whole design

**A Worker cannot rewrite its own secrets at runtime.** Cloudflare secrets are
set at deploy time or through the API; there is no binding that lets request
code mutate them. Self-service password change therefore *requires* moving the
credential into storage the Worker can write — D1.

This is normal practice (the stored value is a PBKDF2 hash, not a password,
and every application stores those in its database), but it does move the
authentication root of trust from Cloudflare's secret store into the
application database, so it is recorded here as a deliberate decision rather
than an implementation detail.

## Scope

In scope:

- One owner account changing its own password from `/admin`.
- Existing sessions elsewhere are invalidated when the password changes.

Explicitly out of scope (decided, not deferred by accident):

- Multiple admin users, invites, or role management. Nobody else logs in.
- Email-based password reset. It adds a public endpoint, a token table, and
  expiry handling; the env fallback below already removes the lockout case
  that reset would exist to solve.

## Data model

Migration `0010_admin_credentials.sql`:

```sql
CREATE TABLE IF NOT EXISTS admin_credentials (
  email TEXT PRIMARY KEY,
  password_hash TEXT NOT NULL,
  role TEXT NOT NULL DEFAULT 'owner',
  password_changed_at TEXT NOT NULL,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
```

Ships empty. No data migration: the table being empty is exactly what selects
the existing env-based behaviour below.

## Credential resolution

`getAdminUsers()` in `src/worker/middleware/adminAuth.js` gains one step in
front of what it already does:

1. If `admin_credentials` has a row for the submitted email, use it.
2. Otherwise fall back to `ADMIN_USERS`, then `ADMIN_EMAIL` +
   `ADMIN_PASSWORD_HASH`, exactly as today.

The env credential is therefore a permanent bootstrap, not a migration step.
Three consequences, all wanted:

- Behaviour is unchanged until the form is used for the first time.
- An empty table, a failed D1 write, or a brand-new environment cannot lock
  anyone out — the env credential still works.
- A fresh preview/production Worker needs no seeding.

D1 unavailability must fall through to the env credential rather than fail the
login. A database blip should not take the CMS offline.

## Change flow

`POST /api/admin/password`, behind the existing blanket `/api/admin/*` gate.

Request: `currentPassword`, `newPassword`, `confirmPassword`.

Server-side rules:

- Verify `currentPassword` against the **currently active** credential
  (whichever of D1/env resolution returns), so the form cannot be used to set
  a password without knowing the existing one.
- `newPassword` minimum 12 characters — matches the floor already enforced by
  `scripts/cms/hash-admin-password.mjs`, so the two paths cannot disagree about
  what is acceptable.
- Reject when `newPassword` equals `currentPassword`.
- Reject when `newPassword !== confirmPassword`.
- Hash with `pbkdf2_sha256$100000$…`, identical parameters to the script.
- Upsert into `admin_credentials` and set `password_changed_at`.
- Rate limited on its own bucket (`admin-password-change`), so a stolen session
  cannot brute-force the current password through this endpoint.
- Audit-logged (`entity_type: 'admin_credentials'`), recording that the
  password changed and when — never the password or the hash.

### Shared hashing

`adminAuth.js` currently derives bits only inside `verifyPassword`. Extract
`hashPassword(password)` beside it, reusing `importPasswordKey` and the same
iteration/length constants.

This matters more than it looks. The generator script hashes with node's
`pbkdf2Sync` and its own base64url encoder while the Worker verifies with
WebCrypto and a separate decoder, and nothing structurally held the two
together — which is the class of mismatch that produced the 2026-09-17
lockout. A regression test now pins the script's output format
(`adminAuth.test.js`); the in-app path must share one implementation so there
is no second format to drift.

## Invalidating other sessions

Session tokens already carry `iat` (`adminAuth.js`, `signSessionPayload`), so
no token format change is needed.

`requireAdmin` gains one check: reject any token whose `iat` predates the
account's `password_changed_at`. One comparison, no per-token bookkeeping, and
it composes with the existing `admin_session_revocations` logout mechanism
rather than replacing it.

The property this buys: if the password is being changed *because it leaked*,
the session an attacker already holds dies at the moment of the change. The
cost is re-login on the owner's other devices, which is the expected behaviour
of "change password" everywhere else.

Ordering note: the change response must issue a fresh session cookie for the
current browser, or the operator logs themselves out by succeeding.

## UI

A "Security" panel in the admin, reusing the show/hide password toggle already
shipped on the login form. Three fields, inline validation, a clear success
state, and an explicit warning that other sessions will be signed out.

## Testing

Unit (`adminAuth.test.js` and a new `password.test.js`):

- D1 credential takes precedence over env when present.
- Env credential still works when the table is empty — the no-lockout property.
- D1 read failure falls back to env rather than failing the login.
- Wrong current password rejected; too-short rejected; mismatch rejected;
  unchanged password rejected.
- A password set through the endpoint verifies through `verifyPassword`
  (round-trip, the same guard the script now has).
- A token issued before `password_changed_at` is rejected; one issued after is
  accepted.

E2E (`admin.spec.js`):

- Change password, confirm the old password now fails and the new one works.
- Confirm a session established before the change is rejected afterwards.
- Endpoint rejects an unauthenticated caller.

## Rollout

1. Apply `0010` to preview, then production. Additive; ships empty.
2. Deploy. Nothing changes until the form is used.
3. Change the password through the UI; verify login with the new password and
   that the env credential is now superseded.
4. Leave `ADMIN_PASSWORD_HASH` set. It is the bootstrap, not dead weight.
