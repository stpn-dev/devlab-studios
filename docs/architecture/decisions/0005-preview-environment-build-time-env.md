# 5. Preview environment via CLOUDFLARE_ENV at build time, not wrangler --env

**Status:** Accepted (Phase 6)

## Context

Standard Wrangler named environments (`env.preview` in `wrangler.jsonc`,
deployed with `wrangler deploy --env preview`) were tried first, since
that's the documented mechanism for any normal Wrangler project. It does
not work with this adapter. Verified directly, not assumed: with an
`env.preview` block defined, `wrangler deploy --dry-run --env preview`
came back showing **production's** D1 database and R2 bucket. Inspecting
the adapter's generated `dist/server/wrangler.json` explained why: it's
generated by `astro build`'s Cloudflare integration step, baked from
whichever environment resolves at *build* time — before `wrangler
deploy` (or Workers Builds) ever runs. Passing `--env preview` at deploy
time is too late; the deploy step just uses whatever `wrangler.json` the
build already wrote, unconditionally. A separate `--config
wrangler.preview.jsonc` file was tried next and rejected too — the
adapter's build-to-deploy handoff is keyed to the specific config
filename it read at build time, so a differently-named file breaks the
handoff entirely and the deploy fails outright with a missing
entry-point error.

## Decision

Keep a single `wrangler.jsonc` with a normal `env.preview` block, but set
`CLOUDFLARE_ENV=preview` as an environment variable for the **build**
step (`CLOUDFLARE_ENV=preview npx astro build`), not the deploy step.
`@astrojs/cloudflare` reads `CLOUDFLARE_ENV` via Wrangler's own
`unstable_readConfig` internally and bakes `env.preview`'s bindings into
`dist/server/wrangler.json` at build time. This was confirmed
empirically: building with and without the env var, byte-diffing the
generated config, and dry-run deploying both — with the env var set, the
dry-run correctly showed the preview D1 database, R2 bucket, and even the
separate `devlab-studios-preview` Worker name (from `env.preview.name`),
regardless of whether `--env preview` was also passed to `wrangler
deploy` afterward.

## Consequences

- The one-time resource provisioning (new D1 database, new R2 bucket,
  preview-only secrets) still had to be documented rather than done here
  — the API token available in this session lacked permission to create
  either resource. See `docs/deployment.md`'s "One-time setup".
- Because the Worker *name* is also part of `env.preview` and gets baked
  in the same way, there's no failure mode where forgetting `--env
  preview` at deploy time causes a preview build to overwrite the
  production Worker — the bound name travels with the bindings from the
  same build.
- Whatever CI or Workers Builds configuration eventually drives preview
  deploys must set `CLOUDFLARE_ENV=preview` on the **build** command, not
  just pass `--env preview` to a deploy command — this is easy to get
  backwards since it inverts where most Wrangler documentation says the
  environment selection belongs.
