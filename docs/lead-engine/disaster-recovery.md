# Disaster recovery

## The claim this document exists to make

**No critical workflow in this system exists only in an external dashboard.**

Every rule, threshold, weight, prompt, compliance profile, schema and piece of
orchestration is a file in this Git repository. Nothing was configured by clicking
in a third-party UI and then forgotten. There is no Zapier scenario, no n8n
workflow, no Make.com blueprint, no vendor-hosted sequence builder, no
prospecting-platform campaign.

Concretely, the things that in other systems live in a dashboard and here do not:

| Would often live in a dashboard | Here |
|---|---|
| Lead scoring rules | `src/lead-engine/config/defaults.js` |
| Qualification thresholds | Same file, `SCORE_THRESHOLDS` |
| AI prompts | `src/lead-engine/ai/prompts/*.v1.js`, versioned |
| Email sequences | **Do not exist.** There is no send capability. |
| Suppression rules | `src/lead-engine/compliance/optOut.js` + `lead_suppression` |
| Compliance checks | `src/lead-engine/compliance/countryProfiles.js` |
| Crawl policy | `src/lead-engine/crawler/` + `CRAWLER` |
| Job orchestration | `src/lead-engine/jobs/` + `lead_jobs` |
| Campaign targeting | A `lead_campaigns` row in D1, editable in the admin, reproducible from `scripts/lead-engine/seed.mjs` |

The Cloudflare dashboard holds bindings, secrets and cron triggers — all of which
are **declared in `wrangler.jsonc`** (except secret *values*, which is the point of
a secret). The Zoho API console holds one OAuth client. Neither holds logic.

If both dashboards were wiped, you would re-enter secrets and re-run a deploy.
You would not have to reconstruct how anything works.

## What exists only as operational data

This is what a backup is actually for. All of it lives in D1
`devlab-studios-cms`.

### Irreplaceable — cannot be regenerated by any means

| Table | Why |
|---|---|
| **`lead_suppression`** | **The most important table in the system.** It is the record of people who asked not to be contacted. Losing it means emailing them again. There is no way to reconstruct it. |
| `lead_messages` | Real conversations with real people. Zoho holds the originals, but the CRM linkage and the analysis do not. |
| `lead_conversations` | Thread ↔ lead linkage |
| `lead_activity` | The append-only audit trail. Losing it means losing the evidence of what was done and when. |
| `lead_compliance_reviews` | Human decisions: recorded legal bases, named reviewers, waivers |
| `lead_contacts` | Provenance URLs captured at a point in time. The page may have changed. |
| `lead_outreach_drafts` | Edited drafts and Zoho draft ids |
| `lead_tracking_tokens` / `_events` | Live tokens in already-sent emails. Losing them breaks those links. |

### Expensive to regenerate — possible but costs money and other people's servers

| Table | Cost to rebuild |
|---|---|
| `lead_companies` | A discovery run (Overpass/Brave requests) |
| `lead_leads` | Same, plus pipeline state and operator decisions **would be lost** |
| `lead_crawl_runs` | Re-crawling every site |
| `lead_signals` | Same |
| `lead_scores` | Cheap **if** signals survive (`scoreLead` is pure); otherwise a re-crawl |
| `lead_ai_runs` | Real Workers AI spend, and non-deterministic — you would not get the same answers |

### Cheap to regenerate

| Table | How |
|---|---|
| `lead_settings` | Defaults come from `config/defaults.js`; only overrides and `business.identity` are lost |
| `lead_campaigns` | `node scripts/lead-engine/seed.mjs` |
| `lead_sources` | Same — but the **policy review** (notes, status, reviewer) is a human judgement and would need redoing |
| `lead_source_records` | A discovery run |
| `lead_jobs` | Transient by nature. Losing it loses pending work, which is re-enqueueable. |
| `lead_usage_daily` | Resets daily anyway |
| `lead_sync_state` | Losing the cursor means re-reading a 7-day window, which is idempotent |

## Backing up D1

Per existing project conventions (see [`../deployment.md`](../deployment.md) and
`docs/operations.md`): D1 data is **not** promoted by a code deploy, and remote
data changes are separate, deliberate, preview-first operations. There is no
automated backup script in this repository.

### Full database export

```bash
# Production
npx wrangler d1 export devlab-studios-cms --remote \
  --output backups/cms-$(date +%Y%m%d).sql

# Preview
npx wrangler d1 export devlab-studios-cms-preview --remote --env preview \
  --output backups/cms-preview-$(date +%Y%m%d).sql
```

This exports the **whole** database — CMS content, the public site's `leads`
table, and all 22 `lead_*` tables. That is the right unit, because they share a
database on purpose (see [architecture.md](architecture.md)).

### Lead-engine-only export

```bash
npx wrangler d1 export devlab-studios-cms --remote \
  --table lead_suppression --table lead_activity --table lead_messages \
  --table lead_conversations --table lead_compliance_reviews \
  --table lead_contacts --table lead_outreach_drafts \
  --table lead_tracking_tokens --table lead_tracking_events \
  --table lead_leads --table lead_companies \
  --output backups/lead-engine-$(date +%Y%m%d).sql
```

### The minimum: suppression

If you do nothing else, do this, and do it before any outreach:

```bash
npx wrangler d1 execute devlab-studios-cms --remote --json \
  --command "SELECT scope, value, reason, source, notes, created_at, removed_at FROM lead_suppression" \
  > backups/suppression-$(date +%Y%m%d).json
```

It is small, it is irreplaceable, and it is the one loss that harms someone other
than you.

### Cadence

There is no automation. A reasonable manual schedule:

| When | What |
|---|---|
| Before applying any migration | Full export |
| Before any bulk operation or reset | Full export |
| Weekly during active outreach | Suppression + messages + activity |
| Monthly otherwise | Full export |

Keep backups **out of the repository** — `lead_messages` and `lead_contacts`
contain personal data. Add `backups/` to `.gitignore` if it is not already
covered.

Cloudflare also provides D1 Time Travel (point-in-time restore within the
retention window):

```bash
npx wrangler d1 time-travel info devlab-studios-cms
npx wrangler d1 time-travel restore devlab-studios-cms --timestamp <ISO-8601>
```

Time Travel restores the **whole database**, which means CMS content too. Prefer
a targeted restore unless the whole database is the problem.

## Restoring

### Whole database

```bash
# 1. Verify on preview first. Always.
npx wrangler d1 execute devlab-studios-cms-preview --remote --env preview \
  --file backups/cms-YYYYMMDD.sql

# 2. Sanity-check
npx wrangler d1 execute devlab-studios-cms-preview --remote --env preview \
  --command "SELECT COUNT(*) FROM lead_leads"

# 3. Then production, with a fresh token
npx wrangler d1 execute devlab-studios-cms --remote --file backups/cms-YYYYMMDD.sql
```

### Suppression only — the case that matters

```sql
-- From the exported JSON, per row:
INSERT OR IGNORE INTO lead_suppression
  (id, scope, value, reason, source, notes, created_by, created_at)
VALUES (lower(hex(randomblob(16))), 'email', 'someone@example.com',
        'unsubscribe', 'import', 'Restored from backup YYYYMMDD', 'restore', datetime('now'));
```

The partial unique index (`(scope, value) WHERE removed_at IS NULL`) makes this
safe to re-run: an already-active entry is ignored.

**Restore suppression before turning the engine back on.** Not after.

### Partial restore into a live database

Import a table-scoped export into a scratch database, then `INSERT OR IGNORE` the
rows you need across. Most `lead_*` tables have foreign keys to `lead_leads` or
`lead_companies` with `ON DELETE CASCADE`, so restore order matters:

```
lead_settings, lead_sources, lead_campaigns
  → lead_companies
    → lead_leads
      → lead_source_records, lead_crawl_runs, lead_contacts,
        lead_compliance_reviews, lead_conversations, lead_activity,
        lead_tracking_tokens, lead_jobs, lead_ai_runs
        → lead_signals, lead_messages, lead_outreach_drafts,
          lead_tracking_events
```

`lead_suppression` and `lead_sync_state` have no hard dependency on that order
(`lead_suppression.lead_id` is `ON DELETE SET NULL`), so they can go first.

## Reconstructing from nothing

If the D1 database were lost entirely and there were no backup.

### 1. Code and schema — trivial

```bash
git clone <repo>
npx wrangler d1 create devlab-studios-cms        # if the database itself is gone
npx wrangler d1 migrations apply devlab-studios-cms --remote
```

All 22 tables, correct, with the reasoning intact in comments.

### 2. Configuration — trivial

```bash
node scripts/lead-engine/seed.mjs > scripts/lead-engine/seed.sql
npx wrangler d1 execute devlab-studios-cms --remote --file scripts/lead-engine/seed.sql
```

Sources registered (disabled, unreviewed) and Campaign 001 recreated exactly.
Every threshold, weight, prompt and budget comes from code defaults.

### 3. Secrets — obtainable, not recoverable

| Secret | How to get it again |
|---|---|
| `ZOHO_OAUTH_CLIENT_ID` / `_SECRET` | <https://api-console.zoho.com/> — the client still exists; the secret is re-readable there |
| `ZOHO_OAUTH_REFRESH_TOKEN` | **Redo the authorization-code flow.** [outreach-handoff.md](outreach-handoff.md) 1.3–1.4. 10 minutes. |
| `ZOHO_ACCOUNT_ID` / `ZOHO_USER_EMAIL` | `GET https://mail.zoho.com/api/accounts` |
| `BRAVE_SEARCH_API_KEY` | Brave dashboard, or regenerate |
| `BROWSER_RENDERING_API_TOKEN` | Cloudflare → API Tokens, or create a new one |
| `CLOUDFLARE_ACCOUNT_ID` | Cloudflare dashboard; also in `.github/workflows/deploy-preview.yml` |

None is unrecoverable. The refresh token is the only one needing a browser
interaction.

### 4. Human decisions — genuinely lost

These cannot be reconstructed from anything:

| Lost | Consequence |
|---|---|
| **Suppression entries** | **You will email people who asked you not to.** The single worst loss in the system. |
| Source policy reviews | Redo them. The seeded `policy_notes` tell you what to check. |
| `business.identity` | Retype it. Trivial but blocking. |
| Pipeline stages, hold/lost reasons, operator notes | Where every lead had got to, and why |
| Compliance waivers and recorded legal bases | Must be re-decided by a person |
| Conversation history and analyses | Zoho holds the messages; the CRM linkage does not |

### 5. Regenerating the pipeline

Once configured, run discovery again. Expect:

- **Different candidates** — OSM and Brave results change.
- **Different signals** — the sites have changed.
- Scores are deterministic *given the same signals*, but the signals will differ.
- **Different AI answers.** Non-deterministic, even at temperature 0.1.
- Real cost: Overpass/Brave requests, crawls of other people's sites, Workers AI
  neurons.
- **Anyone already contacted will look like a fresh lead**, because the history is
  gone. That is the practical harm, and it is why suppression and `lead_activity`
  are the two things worth backing up above all else.

### 6. Zoho as a partial fallback

If `lead_messages` is lost but the mailbox is intact, the sync can rebuild the
last **7 days** (the initial window) of matched conversations — but only for leads
whose `lead_contacts` rows still exist, because matching runs through contact
addresses. Older history is not recoverable through it.

The Zoho mailbox itself is a genuine external record of every message ever sent
and received. It is the one place outside D1 where the actual outreach history
exists, and it is independently backed up by Zoho.

## Failure scenarios

| Scenario | Impact | Response |
|---|---|---|
| Worker deploy breaks the site | Whole site down | Cloudflare → Deployments → *Rollback to this deployment*. D1 untouched. |
| Bad migration | Depends | Never edit an applied migration; write a forward one. Migration 0012 is additive and safe to leave. |
| Engine misbehaving | Crawls, AI spend, or bad drafts | `LEAD_ENGINE_ENABLED = "false"` + deploy. Everything stops; nothing is lost. |
| Accidental bulk delete of `lead_leads` | Cascades to signals, scores, contacts, conversations, messages, drafts, tracking, activity | Restore from backup. D1 Time Travel if recent. **`lead_suppression` survives** (`ON DELETE SET NULL`). |
| Suppression table lost | People get re-contacted | Restore from the suppression backup **before** re-enabling anything |
| Zoho refresh token revoked | No drafts, no sync | Redo 1.3–1.4. No data loss. Sync cursor resumes. |
| Workers AI allocation exhausted | Leads park at `HOLD` | Wait. Nothing is lost or wrongly rejected. |
| D1 outage | Engine halts; public site degrades to static fallbacks | Wait. Jobs stay `pending` and drain later. |
| Overpass bans our IP range | Discovery fails | Sequential + bounded + identified requests exist to prevent this. Manual import still works. |
| Secrets leaked | Credential exposure | Rotate: new Zoho client secret + re-auth, new Brave key, new Browser Rendering token. `redactZohoError` and the log redaction list exist to keep them out of logs in the first place. |

## Pre-outreach checklist

Before the first real email goes out:

- [ ] Full D1 export taken and stored outside the repository
- [ ] Suppression export taken separately
- [ ] The restore path tested once against preview
- [ ] `git log` confirms the deployed commit is pushed
- [ ] Every secret recorded in a password manager (so rotation is a choice, not a
      necessity)
- [ ] The `/crawler` opt-out address (`hello@devlabstudios.com`) is monitored
- [ ] `business.identity.senderEmail` is a mailbox someone actually reads — it is
      the advertised opt-out route
